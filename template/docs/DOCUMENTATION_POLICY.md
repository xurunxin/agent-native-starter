# 文档编写与归档规范

## 目标

让第一次接手的使用者或 Agent 能够 **不阅读历史聊天和任务流水**，找到当下可用功能、使用步骤、源码权威入口、设计理由和待办。信息尽量只保留一个权威位置。此规范参考 [Diátaxis](https://diataxis.fr/) 的四类面向读者的文档，并单独管理规划与历史证据。

## 文件该去哪里

| 文档类型 | 放置位置 / 唯一事实来源 | 记录什么 |
|---|---|---|
| 项目入口 | 根目录 `README.md` | 项目用途、当前可用功能、最短启动方式、稳定状态、文档入口。不写每天的开发计划 |
| 入门教程 | `docs/tutorials/` | 初次用户从零完成一个小目标 |
| 操作指南 | `docs/how-to/` | 具体任务怎么完成、前提与命令 |
| API/配置/CLI 参考 | `docs/reference/`、现有 `docs/subsystems/` | **当前实现**的入口、输入输出、契约、错误与验证方法 |
| 原理与取舍 | `docs/explanation/` | 架构为什么这样设计、限制是什么 |
| 持久决策 | `docs/adr/` | 状态（拟议/接受/替代）、背景、选择、影响；不混入待办细节 |
| 未完成任务 | GitHub/Gitea **Issues / Projects / Milestones** | 谁负责、依赖、验收、进展。为主要计划来源 |
| 需要长篇设计方案 | `docs/proposals/` | 明确“提案 / 未上线”、关联 Issue 和决策期限，采纳后移交 ADR/当前参考 |
| 有时效的实测/历史 | `docs/evidence/`、`docs/archive/` | 固定版本的实验方法与数据、旧决策或历史报告，明确日期和不再代表现状 |
| Wiki | 可选 | 面向非开发人员可编辑的 FAQ/教程；不能与代码库复制出两个可变的 API 真相 |

不存在的子目录无需创建空目录。已有项目的旧目录可保留为重定向/索引，迁移需在独立 PR 中检查引用，禁止一次性无审查重命名所有文件。

## 表达方式

以读者任务命名文档：`how-to/configure-gitea.md`、`reference/cli.md`，不要把 `D5`、`P1`、`Phase3`、`final-final-v2` 放在面向用户的标题中。若必须引用内部代号，首次出现即解释含义并链接到权威 Issue；随后使用人能理解的功能名。

当前事实使用“支持、执行、返回”；未完成的设计使用“计划、提案、尚未实现”，并提供 Issue。不得在 README 或 API 参考里说“此能力将在 Phase 2/D5 完成”。已过期计划不混入当前参考，移入历史归档或保留在关闭的 Issue。

文档写给谁要明确：用户文档给直接操作步骤，维护者文档给源码路径与决策理由，架构文档描述稳定职责，不按聊天时间线记流水账。代码能直接看出的细节少抄；外部接口/行为变更同 PR 更新权威参考。只修改内部实现、无用户可见变化时，不要求额外制造文档。

## 迁移遗留文档的最小步骤

先输出只读清单：每个文件所属类型、是否仍准确、入链/被引用情况，标注 `保留 / 更新 / 合并 / 归档 / 待人工确定`；再按**单个子系统**迁移，补索引和链接，优先改正 README 误导。旧设计代号只保留在固定历史证据中。删除需确保没有独立价值或必要审计保留义务；历史 PR/Issue 链接是天然归档，通常不需要把每个讨论复制到 docs。

完成后一位新 Agent 的最短路线应是：`README.md → docs/README.md → 相关 reference → 源码/验证入口 → 当前 Issue`，不应经过五份不同的 Roadmap。
