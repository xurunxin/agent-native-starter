# 文档整理：按读者的问题组织，而非按 Agent 开发过程组织

先读目标仓库 `docs/DOCUMENTATION_POLICY.md`（或 starter 的对应模板）和已有文档索引；没有时采用 README + Diátaxis 四类读者文档 + Issues/ADR/历史证据分离的最小标准。

## 步骤

1. **先分类，再编辑**。README 负责用户能做什么和最短启动；tutorial/how-to 是教学/操作；reference 是**现在可用**的接口与配置；explanation 说明为什么；ADR 保留已经做出的重要决策；Issue/Projects 负责未来计划；evidence/archive 保存指定日期、版本的历史记录。Wiki 只用于明确面向的受众，不复制另一份活跃 API 文档。
2. 读取实际 CLI/API/构建路径或代码并核对。README 不写“Phase 1 完成 X、D5 将实现 Y”；未实现功能链接到 Issue，不能在 current reference 中当作事实。
3. **最低成本整理**：优先修正文档现有位置的错误，再补一张 `docs/README.md` 入口地图；只有读者需求稳定时才创建新页面。避免每个 Issue、PR 都复制一份 Markdown 报告。重复内容合并为一个权威页面，其他仅链接。
4. **处理历史代号**：提案若必须保留 D5/Phase 等标签，首次给自然语言解释、日期和 Issue；面对新用户的页面直接使用功能名称。已失效计划移动到 archive 或关闭的 Issue，不与当前运行说明混写。
5. **迁移已运行多轮的项目**：给出保留/更新/合并/归档/人工核实清单；对需要改路径的文档检查相对链接、README 入口和源码引用。逐个子系统审阅后迁移；避免一次性移动上百页导致历史链接断裂。
6. 只验证实际改动的链接和一条真实指令（若文档包含命令）；不为纯文档工作启动所有应用测试或计算仓库文件哈希。

## 强制输出

- 一张简短的当前/目标文档导航图与各页面读者
- 清理建议及已处理文档清单、链接/命令验证
- 剩余不确定事实、需要保留的历史和 Issue

## 安全底线

不得擅自改变产品承诺、合并删除具有法律/审计义务的证据、把未发布设计说成事实。无用户授权不能推送或清除远端 Wiki；安全文档和政策变更仍走独立可信审核。
