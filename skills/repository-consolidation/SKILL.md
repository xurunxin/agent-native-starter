# 代码库收敛：保留一种权威实现

使用场景：交接成本上升、源码出现 `foo.v1.ts`/`foo.v1.1.ts`、`old_*`/`backup_*`、平行 package、重复的错误处理或仅为旧开发阶段存在的测试基础设施。本 Skill 是**清理审查流程**，不是自动批量删除命令。

## 步骤

1. **只读定向盘点**：从项目入口 / import / 路由 / 构建脚本 / 运行部署配置追踪实际使用者；按相关子系统搜索同名版本文件与相似 Helper。区分未引用、动态引用、公开 API、数据迁移、真正并行运行的版本。没有调用证据就标“不确定”。
2. **判别兼容是否需要**：该旧实现是否已有真实用户、发布契约、数据库记录或第三方消费者？如果没有，优先修改/保留一个规范命名的文件并删除多余分支。若必须保留，集中在**一个路由/适配入口**，记录旧消费者、退出条件、负责 Issue 和移除时间；不再无限复制新的版本文件。
3. **按模块做一小步**：给出 `保留 / 合并 / 删除 / 暂缓` 对照表。先迁移引用和接口，再删不再引用的旧文件；不要只改文件名留下多个入口。历史代码可通过 Git 提交/tag 找回，不要创建 `*.backup`。
4. **验证影响面**：运行真实调用路径或相关编译/测试，再检查旧文件路径仍是否被使用。不能把全文字符串命中都当作引用；动态加载、持久格式、反射和部署脚本要单独核实。只有高风险行为或稳定化/GA 才升级广泛回归。
5. **更新权威文档**：API/用户操作变更才改 README/reference；弃用方案在 Issue/PR 留痕。清理历史 docs 交给 documentation-curation，不制造一份永久的“清理日志”。

## 交付判断

成果看**有效入口是否减少、独立行为是否保持、交接路径是否变短**，不看删除代码行数。反例：一个外部可见 `v1` 协议仍有付费客户时，不得直接删除；可以采用有退出期限的渐进替换（Branch by Abstraction / Strangler Fig），但删除旧端是设计完成的一部分。

## 强制输出

- 当前权威入口、重复/旧版本清单和调用证据
- 拟移除/保留/暂缓的原因、兼容退出条件
- 实际改动、最小验证、未验证事项与必要人工决策

## 安全底线

不批量猜测删除，不重写数据库格式、不破坏已发布协议；先在独立分支修改，保留 Git 历史与回滚入口，要求高风险修改经可信审批。对未知消费者按未决处理。
